# 变更日志

本文件记录千寻影集（QianXun Album）的重要变更。
格式参考 [Keep a Changelog](https://keepachangelog.com/zh-CN/)，版本号遵循语义化版本。

## [1.6.1] - 2026-10-23

补全 v1.6.0 留下的三块：分享记录管理界面、收藏同步接入、新版本检测。

### 新增

- **分享记录管理**（「更多」→ 分享记录）：表格列出服务端所有短链，含创建时间、图片名、
  短链、访问次数、最后访问时间、状态。支持多选复制、单条/批量撤销、撤销全部有效链接。
  撤销前有确认框，撤销后行变灰标记「已撤销」。
- **收藏同步接入**：`toggle_favorite` 后异步推送单条变更到服务端；扫描完成后延迟 1.2 秒
  从云端拉取并合并（LWW，时间戳大者胜）。**本地 `favorites.json` 仍是权威**，
  云端失败静默不影响本地，下次启动以 LWW 收敛。只合并文件确实存在的收藏，
  避免云端残留污染本地清单。
- **新版本检测**：查 Gitee Releases API 与本地 `VERSION` 比对。
  - 启动后延迟 3 秒静默检测（异步，不阻塞启动），有新版本才弹提示；
  - 「更多」→ 检查更新 可手动触发，无论结果都给反馈；
  - 提示框显示版本号、更新说明（Markdown 做最小可读化）、「打开发布页」按钮；
  - 点「稍后再说」记入 `skipped_version`，同版本不再静默提示；
  - 预发布版本（`prerelease` 或 tag 含 `-beta/-rc`）直接跳过，不提示用户换测试版；
  - 设置中可关闭自动检测。

### 版本比较

用「分段转 int」而非字符串比较——`parse_version("1.10.0") > parse_version("1.9.0")`
判定正确，字符串比较会得出相反结果导致漏提示。不足 3 段自动补零。

### 实测

- 版本比较 5 组用例全对（含 `1.10.0` vs `1.9.0`、`v` 前缀、两段式 `2.0`）；
- Gitee API 实测返回 `v1.6.0`，`has_update()` 对当前版本返回「已是最新」，
  模拟 `1.5.0` 正确检测到更新；
- 分享记录对话框实测拉到 5 条真实记录，摘要显示「共 5 条，其中有效 2 条 · 累计访问 4 次」；
- 收藏同步实测：`toggle` 后云端立即出现 `{"key":"f0.png","favorite":true}`。

### 说明

- 更新检测只查询公开的 Gitee Releases API，不上报任何本机信息（仅标准 UA）。
- 测试期间产生的分享记录与收藏数据已清理（短链全部撤销、`favorites` 表清空）。

## [1.6.0] - 2026-10-23

新增**分享服务端**（Cloudflare Workers）：可撤销分享短链 + 图片内联代理 + 收藏同步。
客户端接入短链生成与撤销。

### 新增：分享服务端（`server/`）

部署于 `https://img.agentstack.vip`，D1 库 `qx-album`。详见 [server/README.md](../server/README.md)。

- **可撤销短链**：右键生成 `/s/<7位base62>` 短链，撤销后访问返回 **410**。
  补上了 OSS 签名链接「无法提前作废」的长期缺口（`docs/OSS_DEV_MANUAL.md` §7 早已记录此限制）。
- **图片内联代理**：剥掉 OSS 的 `x-oss-force-download: true` 与
  `Content-Disposition: attachment`，改为 `inline`，浏览器直接看图。
- **收藏同步**：D1 `favorites` 表，LWW（`updated_at` 大者胜）。
- **鉴权**：预共享密钥 + HMAC-SHA256（Web Crypto），时间窗 300 秒。
- **OSS 只读**：专用 RAM 用户，实测 `GetObject`/`ListObjects` 通过、`PutObject`/`DeleteObject` 均 403。

### 关键实测结论

**OSS 强制下载无法用参数绕过**。2025 年后新建的 Bucket，用默认域名访问图片类对象时
OSS 强制附加两个响应头；`response-content-disposition=inline` 参数**完全无效**：

| 方式 | `x-oss-force-download` | `Content-Disposition` |
|---|---|---|
| 默认签名 URL | `true` | `attachment` |
| ＋`response-content-disposition=inline` | `true` | `attachment`（**参数无效**） |
| ＋`inline; filename=...` | `true` | `attachment`（**参数无效**） |
| 经本服务端代理 | 无 | `inline; filename=...` ✅ |

只有换出口（自定义域名需 ICP 备案，或代理）能解决，代理是免备案的那条路。

### 客户端变更

- 新增 `src/core/share_server.py`：服务端 API 客户端（HMAC 签名、短链增删查、收藏同步）。
- 新增设置项：服务端地址、共享密钥（**DPAPI 加密**，与 OSS Secret 同一套）、启用开关、
  「测试服务端连接」按钮（先 `/health` 再用密钥签一个只读请求验证鉴权）。
- 右键菜单：启用服务端时显示「复制分享短链（可撤销）」与「撤销该图的分享短链」；
  未启用时保持原「复制外链（限时签名）」。
- 短链失败自动降级：弹窗询问后回退到直连签名外链。

### 踩坑记录（都写进了 server/README.md）

- **`wrangler secret put` 会创建新部署并把代码回滚到旧版本**：先 deploy 后写 secret
  会导致运行时 `QX_SHARED_SECRET: MISSING`；更隐蔽的是某次 secret 变更后代码变旧，
  表现为**短链重新出现强制下载头**。正确顺序是「写完所有 secret 后再 deploy」。
- **`workers_dev = true` 会让部署在最后一步失败**，但脚本其实已上传，形成「报错但半成功」。
- **Cloudflare 会拦没有 UA 的请求**：Python urllib 默认 UA 返回 `error code: 1010`，
  这不是 Worker 的响应。客户端互调必须带 `User-Agent`。
- **OSS V4 签名两处非直觉细节**（自研 Web Crypto 实现时踩到）：
  `CanonicalURI` **必须带桶名**（`/<bucket>/<key>`），但请求 URL **不能带**；
  `CanonicalHeaders` 要留**空串**，不能写 `host:...`。这两点靠读 OSS 返回的
  `<CanonicalRequest>` 逐行对照才定位。
- **签名只覆盖路径、不含 query**：客户端与服务端必须在这一点对齐，否则带
  `?limit=...` 的 GET 全部 401。

### 实测记录

服务端 6 步全链路：未签名 401 → 建链 201 → 代理出图 200（`inline`、无 force-download、
PNG 头正确）→ 访问计数 hits=1 → 撤销 200 → 再访问 410。
客户端联调：DPAPI 密钥往返一致、真实建链成功、短链出图 `inline`、撤销后 410。

## [1.5.6] - 2026-10-22

补齐 v1.5.4/v1.5.5 之后仍遗留的三处真实缺陷，均经实测确认。

### 严重

- **扫描器跟随 Windows 目录联接（junction），会无限递归**：`os.walk(followlinks=False)` 在 Windows 上**挡不住 junction** —— 它靠 `scandir` 的 `is_dir()` 判断，而 junction 的 `is_symlink()` 返回 `False`（实测确认）。「照片搬到别的盘、原位置留一个 junction」是很常见的做法，一旦成环，扫描就会一直往下走：实测成环后 60 层目录还在继续，最终会把整个盘扫一遍。新增 `_is_link_dir()`，显式用 `os.path.isjunction()` 判定，判断不了时**宁可跳过也不进**。实测同一成环结构：修复前遍历 61 个目录（仍在增长），修复后只遍历 2 个、正确扫出 5 张图且无重复。
- **缩略图生成整图解码，108MP 图内存峰值可达 1.3GB**：`generate()` 先把原图完整解成位图再缩到 256，而缩略图池是 4 线程 + 预热 8 并发，大图库足以打爆内存。现在在 `convert()` 之前加 `im.draft("RGB", (size*2, size*2))`，让 JPEG 解码器直接降采样。实测 12000×9000：**0.47s → 0.05s（快 9.8 倍）**，且输出与不降采样版本**逐字节相同**（渐变、超宽、超高、小图四种图源全部校验通过）。
- **在线模式缓存目录依赖当前工作目录**：在线库用的是虚拟根 `oss@<bucket>`，它不存在于文件系统上，对它调 `resolve()` 会按 CWD 解析 —— 换个目录启动同一个桶就得到两个缓存目录，清理时互相清不掉。现在虚拟根不做 `resolve()`。实测同一桶在两个 CWD 下由「两个不同哈希」变为「同一个哈希」，真实目录行为不受影响。

### 修复

- **云端对象键冲突会互相覆盖**：`create_upload_worker` 里 `relative_to` 失败的兜底是 `rel = it.path.name`，于是 `pics\x.jpg` 与 `pics\sub\x.jpg` 都算出 `qx/x.jpg`，后传的覆盖先传的，索引里两条记录指向同一个 key。现在库外文件**跳过并计数提示**，不再猜 key；同时对批内撞键做去重告警。
- **扫描不存在的目录会静默显示「0 张」**：`os.walk` 默认 `onerror=None`，目录不存在时既不产出也不报错。现在开头直接抛 `FileNotFoundError`，由 worker 转成「扫描失败」提示。

## [1.5.5] - 2026-10-19

处理 v1.5.4 审查报告中剩余的「轻」级优化项，全部带实测数据。

### 性能

- **图片墙按行索引，不再每帧遍历全部图片**：`relayout()` 现在同时产出「每行首末下标」表，`visible_range()`、`index_at()`、`paintEvent` 全部改为二分定位可见行后只遍历该区间。3000 张实测：`visible_range` 从 **390.7µs 降到 2.5µs（快 157 倍）**；绘制需遍历的格子从 3000 降到 19。原实现每帧对全部 items 做一次循环，2 万张时约 9.5ms 纯开销。
- **重排防抖**：拖动缩略图滑块与拖拽窗口边，原先每次 `valueChanged` / `resizeEvent` 都跑一遍全量 justified 贪心（2 万张约 103ms）。现在各自合并为 60ms 一次的防抖重排。
- **分页卡片缩放缓存**：delegate 每帧对每张可见卡片重做一次 `SmoothTransformation`，现按「指纹+档位+目标尺寸」缓存缩放结果（实测单卡 0.177ms，一屏 12 张约 2.1ms/帧）。

### 修复

- **随机排序不再整屏跳动**：原实现每次 `refresh_view()` 都对当前列表整体 shuffle，删掉一张或收藏一张后所有图的下标都变、位置全乱。现在随机序按「路径 → 排序键」固化，只有「重新随机」换种子时才重建。实测：收藏后顺序完全不变；删一张后其余 9 张相对顺序保持不变；重新随机后集合不变但顺序改变。
- **退出期信号抛 RuntimeError**：`workers.py` 里仍有 7 处裸 `signals.xxx.emit`（Thumb 远端分支、ListWorker、UploadWorker、OnlineDeleteWorker），关闭程序时线程池未收尾会打印 "Internal C++ object already deleted" 栈。全部改为 `_emit()` 包装。
- **大图 HUD 文字在浅色图上不可读**：文件名/页码/缩放比直接画在图片上，白色或浅底图上几乎看不清。现在文字下方铺一条半透明黑底条（实测白色图左上角像素从接近纯白压到 8,8,9）。

### 优化

- **配色统一到 `src/ui/theme.py`**：此前 `styles.qss` 与自绘代码各用一套色值，同一语义存在两处不同取值（QSS 选中用 `#0b57d0`、图片墙选中用 `#31406b`）。现抽出 `theme.py` 集中定义 17 个语义色（背景/卡片/前景/强调/星标/危险/成功等），`wall_view`、`grid_view`、`viewer` 共 25 处裸色值改为引用常量，QSS 的选中主色同步到 `#31406b`，并在文件头注明与 theme 的对应关系。以后换主题只改一处。

### 说明

- 本次改动均为纯优化与体验修复，不改变任何功能语义；图片墙与分页的绘制结果已用离屏渲染逐一验证非空且布局正确。

## [1.5.4] - 2026-10-19

三份独立审查报告（UI/交互、core 与安全、控制层与性能）共回传 60 余项发现。逐条复核后修复其中经实测确认的部分，其余做了验证与说明。

### 严重

- **pHash 矩阵转置写反，会导致误删图片（最严重）**：`_dct_matrix` 把 `(2x+1)` 放在行、`k` 放在列，得到的是 DCT-II 基的转置，之后又按行归一化，`M·Mᵀ` 对角为 0.5156/1.0313/…（非正交）。后果不是"哈希质量略差"，而是**纯色、浅色截图、扫描页全部塌缩成同一个哈希**：实测白/红/绿/蓝/灰/深灰 6 种纯色两两距离全为 0（判为重复的 21 对），浅色文档页之间距离也是 0。在线模式下点「保留最大其余删除」会**永久删除云端原图**。修复只需交换两个索引，实测 `M·Mᵀ = I`。
  - 修复前后对比（50 张样本：30 张不同照片 + 10 张不同文档页各 2 份）：旧矩阵把 **20 张互不相同的图归成 1 个组**，执行「保留最大」会移出 19 张（**9 张误删**）；修复后精确为 10 组、每组 2 张、0 误删。
  - 顺带把 DC 分量从取中位数中排除（它恒为最大低频项，会让首位恒为 1）。
- **拖拽文件夹加载完全不可用**：只重写了 `dragEnterEvent`/`dropEvent`，没有 `dragMoveEvent`。QWidget 默认的 `dragMoveEvent` 不 accept，Qt 据此取消整次拖拽，`dropEvent` 永远不派发——表现为有可放置光标、松手无反应。而用户指南明确承诺此功能。
- **单实例保护失效，会开出两个窗口**：`removeServer + listen` 不是原子操作，两个进程同时启动会互相摘掉对方注册的名字、各自 listen 成功。改用 Windows 命名互斥体（`CreateMutexW`，内核级原子）。另修 `newConnection` 在重型初始化之后才连接导致启动期激活请求被丢弃的问题（改为构造前连接 + 构造后 drain pending）。
  - 实测：旧方案 4 进程并发会出现 2 个主实例；命名互斥体 3 轮均为 1 个。**附带说明**：起初试过 `QLockFile`，本机实测 4 进程并发会有 2 个同时拿到锁，不可靠，故未采用。

### 性能（实测数据）

- **子文件夹筛选从数秒降到毫秒**：`_item_folder()` 对每项调用 2 次 `Path.resolve()`，而 `resolve()` 在本机单次实测 **1.92ms**（比 `os.path.abspath` 慢 **1565 倍**），`refresh_view` 又对每项调两次 `_item_folder` → 千张库约 4700ms。改为 `abspath` + 前缀比较，并把结果缓存到 item 上、每项只算一次。实测 `set_folder_filter` **0.4ms**、`available_folders` **0.0ms**。
- **收藏/移出不再触发整库重扫**：`favorites.json` 写入库根、`Remove/` 内移动都会改根目录 mtime，触发 800ms 防抖重扫，把页码和文件夹筛选一起清掉。新增 `_suppress_watch()`，程序自身写入期间忽略目录事件。

### 修复

- **大图解码回调索引越界**：重扫/换库后 `view_items` 变短，`_on_decoded` 直接取值会抛 `IndexError`。加边界检查。
- **点过悬浮按钮后键盘全失效**：按钮点击后获得焦点，`ViewerOverlay.keyPressEvent` 不再收到按键，←/→/R/Esc 全部失灵。四个按钮改为 `NoFocus`。
- **搜索框内 Ctrl+S/Ctrl+O 仍触发全局快捷键**：`QLineEdit` 只遮挡普通字符键，不遮挡组合键——在搜索框里按 Ctrl+S 会对着旧选择静默另存文件。`_guard` 增加输入框焦点判断。
- **翻页后误开大图**：`_last_click_row` 存行号，翻页后行号指向另一张图。改存 `(路径, 页码, 视图模式)`。
- **分页「上次页码」100% 恢复失败**：分批扫描时首批只够 1 页，`min(page, total-1)` 把页码就地夹成 0 且不再恢复。新增 `_pending_page` 期望值机制，页数够了才落地。
- **图片墙不支持触控板**：只读 `angleDelta`（触控板为 0），事件还被吞掉。加 `pixelDelta` 回退。
- **卡片角标污染信息行字号**：画 ★ / 重 角标时改了 painter 字体且未复位。改为成对 `save/restore`。
- **垃圾桶内按 Del 二次移动**：会把文件在 `Remove/` 里再改名，并往 `.qx_removed.json` 写入指向 `Remove/` 的原路径。现在拦截并提示改用「还原」。
- **垃圾桶模式清理孤儿缓存会清空主库缓存**：`cache_root` 仍是主库而 `all_items` 只有 Remove 内容，主库缓存全被判为孤儿。加 `trash_mode` 与 `_scan_finished` 双重前置。
- **一次缩略图失败就永久标记"已损坏"**：网络盘抖动一次就再也不重试、不上传、不查重。改为失败计数，≥3 次才认定损坏。
- **`favorites.json` / `oss_index` 非原子写**：解析失败后原生实现按「空」处理，下一次写入会把用户全部最爱静默覆盖。改为临时文件 + `os.replace`；损坏文件另存 `.corrupt` 且进入只读模式不再覆盖。
- **`_rel_key` 退化成文件名导致云端覆盖**：库外文件 `relative_to` 失败后取 `item.path.name`，不同子目录的同名图算出同一个 key（`qx/x.jpg`）互相覆盖。改为返回空串并由调用方跳过。
- **`_cloud_keys` 一次列举失败永久缓存空集**：之后所有分享都误报"尚未上传"。失败时保持 `None` 以便重试并提示。
- **上传可连点重复启动**：同一文件被并发上传多次。加 `_running` 标志 + 按钮禁用。
- **`QPixmapCache` key 不含 mtime**：外部改了同名图片后 F5 重建了磁盘缩略图，界面仍命中旧 pixmap。key 改用缓存指纹（含 size/mtime）。
- **在线原图临时缓存无上限**：本机实测已无声增长到 **753.6 MB**，且没有清理入口。加 2GB LRU 上限（按访问时间淘汰），并在缓存管理里显示与清理。
- **配置 OSS 后父对话框状态不刷新**：保存返回后仍显示「未配置」。

### 复核后未采纳 / 未能复现

第三方 UI 审查回传 10 项发现，逐条复核后修复 9 项（1 项未复现）。全部经离屏实测验证。

### 修复

- **图片墙焦点与选择不同步（重要）**：方向键只移动蓝色焦点框，不更新 `selection`。实测焦点移到 p21 后按 `Del`，被移出的却是 p04——**移错文件**。现方向键移动焦点同时同步 `selection` 与 `_anchor`。

- **触控板滚动反向**：`wheelEvent` 只看 `angleDelta()`，触控板/高精度设备该值为 0，于是所有滚动都被当成「向下」而持续缩小（一个 ±10 的量就缩到 0.87）。现 `angleDelta` 为 0 时回退到 `pixelDelta`。
- **双击缩放突破上限**：双击「适应窗口」直接取 `_fit_scale()`，小图会算出十几倍放大（40×40 图实测到 17.10×，而 `MAX_SCALE=8`）。现夹取到 `min(fit, MAX_SCALE, 1.0)`。
- **垃圾桶模式关窗污染 last_dir**：垃圾桶下 `root` 指向 `<库>/Remove`，`closeEvent` 把它当「上次浏览的库」存下，下次启动直接把 `Remove` 当普通图库加载。现优先记录 `main_root`。

- **子文件夹下拉与过滤失步**：原目录消失后，下拉回到「全部文件夹」但 `folder_filter` 仍保留旧值（结果为空）。现 `_refresh_folders` 反向同步真实筛选状态。
- **筛选 0 结果无空态提示**：原来只在 `all_items` 为空时提示，搜索/筛选过滤到 0 张时界面一片空白且无解释。现区分「正在扫描」「垃圾桶为空」「目录无图」「筛选无匹配」四种文案。
- **垃圾桶与在线库互斥只做一半**：先勾垃圾桶再开在线库，`delegate.trash_mode` 仍为 `True`，卡片按钮继续显示「还原」（在线模式下点了会走本地还原逻辑）。现双向复位。
- **危险操作补确认**：缓存管理「清空全部缓存」与「清理孤儿缓存」此前无任何确认，现均加确认框（清空前显示文件数与占用）；重复组「保留最大/最新」加 `_busy` 防连点，避免同组被重复移出。

### 未复现

## [1.5.2] - 2026-10-19

承接 v1.5.1 审查，补齐此前未深挖的两处。

### 修复

- **大图浏览器缩放到 0 倍 / 潜在除零**：`_fit_scale()` 在控件尚未完成布局（宽或高为 0）时返回 0，随后 `_scale = min(fit, 1.0) = 0`。此时 `wheelEvent` 里的 `(mouse - center - offset) / _scale` 会除零。实测原本靠 `_pix.isNull()` 提前返回「侥幸」挡住，一旦在布局完成前就拿到图，就会崩或卡在不可缩放的 0 倍。现 `_fit_scale()` 对空 rect / 零尺寸图返回 1.0，并在 `wheelEvent` 入口再兜一层 `if not self._scale`。

## [1.5.1] - 2026-10-19

### 安全修复

- **路径穿越（重要）**：`Remove/.qx_removed.json` 是可被外部编辑的文本，其中记录的「原相对路径」此前被直接拼接后用于还原位置。若该文件被写入 `../../x.png` 或绝对路径，图片会被还原到图库之外（写入任意可写目录）。新增 `file_ops.safe_join()`：归一化后强制校验公共前缀，`..`、绝对路径、无法解析一律拒绝并回落到图片根目录。实测 7 种穿越写法全部被拦，合法子目录还原不受影响。
- **移出时记录越界路径**：源文件不在图库内时改记文件名（原记绝对路径，还原时会写出库外）。

### 修复

- **大图浏览器快捷键误触发（重要）**：`QShortcut` 是窗口级快捷键，其匹配**先于** `viewer.keyPressEvent` 派发。此前只有 F/Del/Ctrl+S/Ctrl+C/Ctrl+O 挂了 `_guard`，而 `R` 没有——在大图里按 `R` 旋转时，会连带把列表中选中的图片「还原」出垃圾桶；`F5`/`F11` 同样不受保护。现统一由 `_guard` 在 viewer 可见时一律让位。
- **缩略图永久卡死**：`_queued` 集合只增不减（`_on_thumb_ready` / `_on_thumb_failed` 均未移除键），一旦某张图的缩略图生成失败或任务被取消，该 `(路径, 档位)` 永久留在集合里，之后永远无法重新排队。现两个回调都 `discard`。
- **缓存写入竞态**：`thumbnail.generate()` 直接写目标 JPEG，多 worker 并发请求同一张图时可能读到半个文件而落成损坏缓存。改为先写临时文件再 `os.replace` 原子替换，异常时清理临时文件。
- **上传索引每张重写**：`UploadWorker` 每成功一张就 `index.save()` 重写整个 JSON，千张库意味着上千次全量磁盘写。改为每 20 张批量落盘 + 收尾兜底。
- **滚动位置从未被正确保存**：`closeEvent` 保存的是 `self.view`（分页网格）的滚动条，而恢复时写入 `self.wall`（图片墙），两者不是同一控件，导致滚动记忆完全失效；且分页模式下也去恢复图片墙滚动位置。现保存与恢复统一走 `self.wall`，并只在滚动模式恢复。
- **非模态对话框闪退**：缓存/上传/重复面板用 `Dialog(...).show()` 创建，仅由局部变量持有，Python GC 会在窗口显示后立刻回收对象导致闪退。现由主窗体持有引用（`_dlg_cache` / `_dlg_upload` / `_dlg_dups`）。

### 性能优化

- **扫描期刷新节流**：此前每收到一批扫描结果就 `refresh_view()` 全量重排 + `beginResetModel` 重建模型。2000 张库单次 `refresh_view` 实测 13.22 ms，32 批累计约 423 ms 的纯重复开销，扫描期明显卡顿。现合并为最多每 150 ms 刷一次，扫描结束再强制刷一次。
- **`row_of_path` 线性查找**：每张缩略图就绪都会调用，原实现对整表线性扫描（2000 张时单次约 0.2 ms，累计 O(n²)）。改为 `set_items` 时建立「路径 → 行号」字典，实测 10 次查找 0.014 ms，**快约 140 倍**。
- **图片墙每帧重复缩放**：`paintEvent` 对每个可见格每帧都做一次 `SmoothTransformation` 平滑缩放。改为按「路径+档位+格尺寸」缓存已缩放结果，命中即直接贴图。

### 体验优化

- **批量移出增加确认**：`Del` 在多选状态下会一次性移出整批文件（虽可还原），此前无任何确认。现选中 ≥2 张且不在垃圾桶时弹确认框；单张保持一键移出，不打断高频操作。
- **长宽比输入边界**：`parse_aspect` 此前接受 `inf`/`nan`（`1e400` 之类会解析成 inf），会让 `abs(log(ratio/target))` 变成 inf/nan 导致筛选结果全灭或全过。现统一拒绝 0、负数、inf、nan，并捕获 `ZeroDivisionError`。

### 修正说明

- 本次审查中一度误判 `scanner.scan_batches` 的 `errors` 归零为缺陷并做了改动，实测后确认**原设计正确**（`ScanWorker` 侧负责跨批累加，若扫描器也返回累计值会重复计数），已完整回滚并补充注释说明「stat 失败才算错误，解不出分辨率的走 `corrupted` 标记」。
- 同样一度误判分页页码未夹取上界，实测确认 `_apply_to_model` 在分页模式下已正确夹取（滚动模式下 page 无意义），无需修改。
